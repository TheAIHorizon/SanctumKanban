Gantt / Timeline view

A second view of the same team tickets—not a second task database.

Delivery boundary: this feature is developed and tested locally. A GitHub push is not a deployment. Do not update the live student NAS or restart its containers without a separately approved rollout.

How to use it

  1. Select the class workspace, then choose Gantt beside Detailed, Overview, and My Teams.
  2. Select all visible teams or one team. Expand/collapse each team heading.
  3. Switch between Week and Month; use Previous, Next, and Today. Narrow screens scroll within the chart, with ticket names retained at the left.
  4. Click a ticket name or bar. Authorized members/leads/admins see the existing editor. Others see read-only details. Archived classes remain read-only even for admins.
  5. Set an optional Planned start date and Due date. Save to place or move the bar. Kanban and Gantt refer to the same ticket.

Bar colors follow the assignee; unassigned work uses a neutral color. Status is shown as Backlog, Doing, or Done. Overdue markers exclude Done tickets. The today marker is a calendar guide, not a progress measurement.

What the dates mean

Ticket datesGantt behavior
Start and due dateScheduled bar; both days are included.
Same start and due dateOne-day bar, not an invisible zero-duration task.
Either or both dates missingVisible in Unscheduled, with the missing-date reason.
Dates outside the displayed week/monthCounted separately as outside this range; never mislabeled Unscheduled.
Start later than due date / impossible dateRejected in the editor and API; the existing ticket is not changed.

Creation dates are never substituted for planned start dates. Existing tickets retain their due dates and begin with no start date. Dates entered through the editor are calendar dates normalized consistently; the API retains compatibility with explicit timezone-qualified ISO due timestamps, interpreted on the UTC calendar for timeline display.

This version intentionally has no bar dragging/resizing, task dependencies, automatic scheduling, critical-path calculation, percentage-complete guesses, or live collaboration subscriptions. Refresh to see another user's edits.

GA acceptance checklist

  • One ticket appears in both Kanban and Gantt; editing dates changes the same record.
  • New and existing tickets can have no dates, one date, or both dates.
  • One-day, overdue, Done, unassigned, cross-month, and far-future tickets behave as described.
  • Switch teams and classes: only the selected class's permitted teams appear.
  • Student edits permitted tickets; peer-team tickets and guest views are read-only.
  • Archived-class dates cannot be edited, including through direct API requests.
  • Week/month navigation, Today, horizontal scrolling, and keyboard activation work.
  • Existing Kanban creation, reordering, comments, tags, and notes still work.

Later NAS rollout — not performed by this feature work

  1. Choose a maintenance window with the instructor; confirm no automated deployment will pull the new GitHub commit ahead of that window.
  2. Inspect the current NAS image, schema, Compose configuration, and data volume. Keep its environment/credentials and networking intact.
  3. Create a protected database backup and retain the previous image. Restore the backup to a separate test database and rehearse the update.
  4. Review the additive migration prisma/migrations/20260915_add_ticket_start_date/migration.sql: it adds a nullable DATE column only—no defaults, backfill, ticket deletion, or date rewrites. Choose the deployment's established migration/schema-sync procedure; this repo has legacy db-push installations, so do not blindly run migrate deploy against an unbaselined database.
  5. Build and verify a linux/amd64 image. The existing entrypoint runs Prisma schema sync on start; review that behavior before any container restart.
  6. At cutover, pause app writes, take the final backup, apply the reviewed additive schema change, and replace only the app container. Do not remove the PostgreSQL volume or seed/reset the live database.
  7. Verify user/team/ticket counts, existing data, login through the GA's actual HTTPS URL, scheduled/unscheduled rendering, date persistence, and permissions. Check TLS separately from application health.
  8. If rollback is needed, restore the previous app image. Leave the unused nullable column in place; deleting the column would erase newly entered start dates. Restore database data only through a deliberate recovery plan.
This feature does not resolve the separately documented pre-existing cross-class ticket/report authorization issues. Review the code-review notes before a broader release.
