AI Coach: clearer tickets, grounded DCWF suggestions

Advisory feedback powered by the user-owned CoyoteGPT service using Laguna S (model ID laguna-s).

Using the coach

  1. Create or open a ticket you are permitted to edit.
  2. Write the title and description, then select the AI Coach tab.
  3. Choose Ask AI Coach. Merely opening the tab does not send a request.
  4. Review the questions and suggested DCWF Tasks. Edit the description yourself if the advice is helpful.
  5. Use the existing DCWF picker to deliberately select/link an appropriate task. Advice does not save ticket text, attach tasks, mark work complete, or award a grade.

For “Installed Ubuntu Server,” the coach should ask what was installed, how it was tested, and which observable result verified success. It should not conclude that testing was never performed merely because it was not documented.

Changing the draft clears old advice. Feedback for one ticket must never be shown as advice for a different ticket. Existing observer/peer-team/archived restrictions remain enforced by the server.

Saved nightly guidance

Manual Ask AI Coach remains user-triggered and does not save advice automatically. If an instructor enables nightly review for the class, a separate background worker reviews eligible saved ticket text and stores clearly labeled guidance. This automatic path is distinct from the draft button and requires explicit class opt-in. See nightly reviews and instructor feedback.

How grounding works

  1. The application searches its imported DCWF Task records using deterministic keyword and synonym relevance, including common terms such as AD, DNS, and SSH.
  2. Only positively relevant records become candidates; there is no arbitrary list of unrelated tasks when nothing matches.
  3. Laguna S receives the current draft and a bounded set of retrieved task excerpts. It returns structured feedback and suggested candidate IDs.
  4. The server validates that output. Every displayed task ID, official description, role mapping, and source excerpt comes from the eligible database records, not invented model citations.
  5. When no relevant record exists, the system abstains and asks for clearer technical details.

This is structured retrieval-augmented guidance, not a newly installed vector database. Source references identify the imported DCWF record by its exact string ID and wording. The current import does not preserve workbook worksheet/row provenance or guaranteed per-record version metadata, so the UI does not invent those citations. Keep the source import under administrative control.

Privacy and limitations

Manual coaching sends the draft title/description plus retrieved reference excerpts after the user clicks. Enabled nightly review sends eligible saved title/description text automatically. Separate profiles, comments, and other team records are not loaded for the model. Free text can still contain personal information or secrets: do not include passwords, private keys, or unnecessary personal data.
  • Requests go to the configured user-owned CoyoteGPT endpoint over its configured transport. The app does not log prompts or raw model payloads; model-server logging/retention is a separate administrative setting.
  • The model is an adviser, not a grader, verifier, or source of authoritative new DCWF records. Review its reasoning; grounded IDs do not make every explanation infallible.
  • Ticket text is treated as untrusted data. Generated text is rendered as text, not executable HTML. Model output cannot automatically change application records.
  • No numeric model-confidence scores are presented as calibrated certainty.
  • Manual button advice is not stored automatically; enabled nightly review stores separate guidance records. Changes to ticket text or task links still require the user's normal actions.

Fallback and service behavior

A valid model answer is labeled CoyoteGPT response and identifies the model. If the service is unreachable, times out, or returns invalid output, the app uses clearly labeled Keyword fallback guidance and canonical task matches. Fallback is not a successful AI response. Users can continue normal ticket work without the AI service.

Coaching requests have a bounded model timeout and per-user limits. A rapid repeat may return “wait and try again.” Request errors are displayed and do not leave the form permanently loading.

The dedicated AI_COACH_MODEL setting defaults to laguna-s. It reuses the existing AI_BASE_URL and AI_API_KEY configuration. It does not require replacing the other AI feature's AI_MODEL setting or publishing credentials.

Acceptance checks

  • A vague installation ticket gets testing/verification questions, without fabricated results.
  • A detailed ticket is not automatically rewritten or graded.
  • Every proposed task ID and displayed excerpt match a real imported Task record.
  • Nonsense with no matches yields no forced task assignment.
  • Instruction-like text cannot introduce arbitrary task IDs or cause writes.
  • Changing a draft invalidates its old advice; errors and retry states are clear.
  • Unauthorized and archived-ticket requests are denied before inference.
  • A real laguna-s request is verified separately from fallback behavior.

The guarded scripts/ai-coach-check.mjs exercises the real model and browser using synthetic local fixtures only. Never aim fixture tests at live student data.
