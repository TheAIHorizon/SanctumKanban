Live student site: operations and safety

Students use this site. Their work is not disposable. Read the full OPERATIONS.md runbook and the private .ops/site.local.json inventory before work. Missing inventory means obtain the real target—not guess.

How the service works

Browser → public DNS/DDNS → router port forward → Synology HTTPS reverse proxy/certificate → Kanban app container → PostgreSQL container → persistent database volume.

The app image, database, TLS certificate, router/DNS path, and browser are separate layers. The private inventory records exact names, paths and ports without passwords. It is deliberately excluded from the public GitHub repository.

Local testing, GitHub publication, and live deployment are different outcomes. A local page or running container is not proof that students can reach the shared URL.

Required release order

Test → commit → push to GitHub → verify the remote commit → deploy that exact commit to the NAS.

Approval to deploy tested changes also authorizes committing and pushing their code, tests, and documentation first, without a separate publication confirmation. Local-only work does not imply publication or deployment approval. Keep private configuration, secrets, and backups out of Git. If the push or remote verification fails, leave the live deployment unchanged. Never deploy unpublished or uncommitted application changes.

Before a live update

  1. Obtain explicit approval for the live update and a short write pause.
  2. Test the exact shared URL before changing anything; record TLS, redirects, and the intended user/network path.
  3. Inspect the actual running image/revision, Compose project, mounts, and student-data baseline.
  4. Commit and push the tested release, verify its exact commit on GitHub, and build the candidate from that clean published source for the NAS architecture before the outage.
  5. Back up the database and configuration, retain the previous image, restore the backup into a separate rehearsal database, and verify the reviewed schema changes preserve existing records.

Cutover and acceptance

  1. Pause only app writes and take a final consistent backup.
  2. Apply only the reviewed schema changes; compare existing counts and content fingerprints.
  3. Replace only the app container against the unchanged database volume and preserved configuration.
  4. Verify schema, image revision, data, authentication and the changed feature.
  5. Check the exact public hostname/port with normal TLS verification. Verify external access and the user's relevant internal-network path.

If the app is running but public access is blocked, say exactly that. Do not call the site ready for students on the strength of a different hostname, an insecure TLS bypass, or a LAN-only test.

Never do these on live student data

  • No demo reseeding, database reset/drop, or volume removal.
  • No docker compose down -v.
  • No local/demo database replacing the live one.
  • No blanket schema sync with accepted data loss.
  • No incidental changes to DNS, router rules, certificates, passwords, or session secrets.
  • No raw student records, credentials, environment files, or database dumps in Git or chat.

Recovery

For a compatible additive migration, revert the app image and retain the unused new columns. Do not erase new student evidence by dropping columns or restoring an older database over later writes. Keep backups and inspect before retrying any interrupted operation. An approval timeout is not consent.

The access incident: separate the evidence

A certificate was already assigned, but the hostname it covered differed from the Kanban hostname. That explained a TLS validation error; it did not prove the cause of a later Windows TCP timeout.

The Windows device resolved the expected public IP, failed TCP to the public HTTPS port, and successfully reached the NAS HTTPS port over both Ethernet and Tailscale. Phone access worked. This points toward a path/loopback/filtering difference, not necessarily an application failure; the precise router cause was not conclusively isolated. No certificate or router repair was performed. Preserve that distinction instead of repeating an unsupported diagnosis.
