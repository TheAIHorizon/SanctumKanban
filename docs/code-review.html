Review record

Code Review & GA Findings Resolution

Architecture-oriented review of the current class workspace, ticket workflow, observer, collaboration, deliverables, and verification changes for the student enterprise IT build-and-defense use case.

Review status: this document is not an independent security audit, does not claim that acceptance testing has passed, and does not declare the application production-safe. Items marked RESOLVED IN CHANGE SET describe code paths and tests present on disk; runtime acceptance must be supported by generated evidence.

1. Purpose and review boundaries

Sanctum Kanban coordinates team execution and captures evidence: class-scoped boards, assigned work, history, comments, DCWF task reflections, weekly reflections, and reports. The reviewed change set extends this model with class lifecycle management, global instructor deliverables, student resource links, persisted ticket ordering, shared notes with optimistic concurrency, an observer experience, and repeatable system checks.

This review inspected the relevant UI components, authorization helpers, API routes, Prisma schema, system-check scripts, and tests. It is a targeted code review, not exhaustive threat modeling, dependency auditing, infrastructure review, browser compatibility certification, load testing, or penetration testing.

2. Architecture

Presentation

Next.js App Router pages and React client components render the dashboard, class switcher, team views, Kanban cards, filters, dialogs, shared notes, resources, reflections, and reports.

Application/API boundary

Next.js route handlers authenticate with NextAuth sessions. Central can() rules cover core ticket/report actions, while class, note, resource, reflection, and lifecycle routes add resource-specific checks.

Persistence

Prisma targets PostgreSQL. ClassWorkspace owns teams/resources/members; tickets retain status and integer position; TeamNote.revision enables compare-and-swap saves; archived state preserves records.

Evidence and verification

Node/TypeScript tests cover pure rules and route contracts. check:system runs tests, lint, and build and emits JSON. A separately guarded integration script exercises real HTTP sessions and an isolated PostgreSQL fixture.

Important trust boundaries

  • The browser is not trusted to enforce authorization; API routes must reject forbidden direct requests.
  • Class enrollment determines ordinary class visibility, but observer visibility is intentionally broad and read-only.
  • Team membership and ticket ownership determine writes; archived classes add a read-only lifecycle boundary.
  • Shared notes and board content are collaboration data, not confidential storage.
  • The optional local-AI DCWF suggestion path must degrade to keyword search and must not become a dependency for ticket logging.

4. Open findings — FOLLOW-UP (not fixed)

These are actual pre-existing/current behaviors observed in source. They are not silently converted into documentation assumptions, and none is marked resolved.

F-01 — Ticket list and detail GET lack class-enrollment scoping FOLLOW-UP

GET /api/tickets permits every authenticated principal to list across teams (with optional filters), and GET /api/tickets/[id] returns a ticket to every authenticated principal by ID. Neither route checks class membership. This mirrors the broad “authenticated principals can read any board/ticket” policy, but it is wider than ordinary student class-workspace visibility and can expose ticket metadata across classes through direct API use.

Recommended resolution: decide and document one authoritative read policy. If enrollment isolation is intended, scope list results by visible class membership and check ticket.team.classWorkspace membership in detail GET, with explicit admin/observer rules and negative tests. Review comment and DCWF subresources for the same policy.

F-02 — Ticket PATCH/tag validation, atomicity, and assignee integrity FOLLOW-UP

  • PATCH /api/tickets/[id] accepts tagIds without proving it is an array of unique existing tags allowed for that ticket’s team (team tag or global tag).
  • It deletes old ticket-tag links and recreates them before the ticket update, outside a transaction. A later foreign-key/validation/update failure can leave tags removed or partially changed.
  • The PATCH route can assign an arbitrary user ID and does not repeat the create route’s “assignee must belong to this team” validation.
  • Title, status, due date, and tag payloads lack a single explicit schema; invalid Prisma values tend to collapse into a generic 500 rather than a stable 400.
  • PATCH /api/tags/[id] also conditionally applies truthy name/color without explicit format/length validation.

Recommended resolution: parse a strict schema, validate team/global tag scope and assignee membership, and perform ticket fields, tag replacement, and history writes in one transaction. Return deterministic 400/403/409 responses and add rollback tests.

F-03 — Global keyboard shortcuts fire on every mounted team board FOLLOW-UP

Each TeamKanban registers a document-level listener. In Detailed or My Teams view, pressing N, M, E, ?, /, or Esc can affect all mounted boards; search focus selects the first matching input. A currently unused global shortcut registry also deduplicates by key rather than active board context.

Recommended resolution: move shortcut ownership to the dashboard/focused-board level or require an active team context. Test multi-board behavior and accessibility.

F-04 — Previous-week reflection content is reused FOLLOW-UP

The dashboard loads only the newest reflection per team. ReflectionBoard sets current-week fields from that record even when its weekOf is older, then saves them under the current week. The computed isCurrentWeek value is not used to clear or label inherited content.

Recommended resolution: initialize blank fields when the newest record is not for the current week, or offer an explicit “copy previous week” action. Add a week-boundary test.

F-05 — No live updates KNOWN LIMITATION

There is no WebSocket, Server-Sent Events, polling, or subscription layer. Client state updates only for the current action and via navigation/refresh. Team-note revisions prevent silent overwrite but do not stream changes.

Recommended resolution: retain the manual-refresh contract unless authenticated real-time rooms, reconnect behavior, authorization, and concurrency tests are designed and implemented.

F-06 — No forced first-login password flag FOLLOW-UP

The cohort provisioning route creates accounts with a temporary password and tells callers students should change it, but the User schema has no mustChangePassword field and login does not force a password-update flow. The default fallback temporary password in source increases deployment risk if not overridden.

Recommended resolution: add a persisted first-login/password-reset state, force the flow before ordinary app access, expire temporary credentials, require a deployment-provided strong temporary-password process, and test bypass attempts.

F-07 — Concurrent collaboration writes FIXED; TARGETED CHECKS PASS

Resource replacement now checks an expectedResources baseline under a class-row lock and returns 409 for stale submissions. Notes keep authorization, revision compare-and-swap, and read-back in a locked transaction. Reordering locks and rechecks the current ticket, target, team, class, and membership inside its transaction. Retryable serialization/deadlock failures return 409. The real HTTP test confirms that a stale resource edit does not overwrite the winning edit. Unit/contract tests cover transaction structure; they are not an exhaustive concurrency stress test.

Deliverable distribution retains its serializable transaction. Concurrent submissions can require a retry; broader concurrency stress testing remains recommended.

Additional authorization findings — still open

Deployment caution: the passing GA tests do not establish complete cross-class confidentiality. Resolve the report and ticket read-scope issues before relying on this application to isolate sensitive student evidence between classes.

  • High priority: student report scope. src/app/api/users/[id]/report/route.ts:34-136 authorizes a lead through any shared team, then accepts an arbitrary team filter or no team filter. Profile memberships, activity, DCWF evidence, and alignment can extend beyond the authorized teams. src/app/api/users/[id]/report/export/route.ts:39-91 similarly exports evidence across teams. Derive allowed team IDs server-side and apply them to every query and alignment calculation; reject unauthorized filters. Add cross-class lead regression tests.
  • Roster lifecycle policy needs clarification. src/app/api/teams/[id]/members/route.ts:149-158 removes only team membership, leaving class enrollment intact. Removing someone from their last team therefore does not revoke class visibility. Decide whether class enrollment is independent; provide explicit class unenrollment or transactional cleanup consistent with that policy.
  • Global-tag creation scope. src/app/api/tags/route.ts:63-99 permits a TEAM_LEAD to create a global tag by omitting teamId. Restrict global creation to admins and enforce own-team scope for leads.
  • Former comment-author writes. src/app/api/comments/[id]/route.ts:17-35,56-82 checks authorship but not current membership, allowing departed authors to edit/delete old comments in active classes. Define retention policy and enforce current access if removal must revoke writes.

These are current source-inspection findings, not newly exercised production exploits. The older review's stale-JWT finding was fixed in this change set and is covered by authorization regression tests; its intermediate test failure is superseded by the final successful verification.

6. Review observations by control area

Authorization strengths in the change set

  • Observer write denial is represented in centralized ticket rules and reinforced on profile, notes, middleware, and UI paths.
  • JWT session reads refresh current role/user state from PostgreSQL, so role changes and deleted users do not rely solely on stale login claims.
  • Reorder validates same team, same status, active ticket state, class write state, and ticket update permission before a serializable position transaction.
  • Resources are admin-write-only and accept only HTTP(S) URLs without embedded username/password.
  • Deliverable distribution is admin-only, blocked when archived, and performed in a serializable transaction.
  • Team Notes use a revision predicate rather than last-write-wins.

Operational caveats

  • Archived-class protection is distributed across routes. Future mutating routes must add the same lifecycle guard and tests.
  • The observer identity is created lazily during guest sign-in, so even “read-only observer login” writes that singleton user if absent. This is distinct from board-content writes.
  • Default check:system is suitable for code/build verification and optional unauthenticated HTTP status checks; it is not a logged-in end-to-end exercise.
  • The integration fixture cleans up in finally, but interrupted processes or infrastructure failure can leave disposable records. Verify cleanup before destroying the disposable database/service.
