Sanctum Kanban User Manual

A practical guide for coordinating an enterprise infrastructure build, documenting defensive work, and turning tickets into auditable evidence of team and DCWF progress.

Scope. This manual describes behavior implemented in the current application. Sanctum Kanban is a shared coordination and evidence system—not a confidential notebook, secrets vault, automated security scanner, or real-time chat system.

1. Purpose: build, defend, and show the work

Use the board as the operating record for a student enterprise IT environment. A useful ticket is small enough to assign, specific enough to verify, and complete enough that another teammate can understand what changed. Typical work includes network and identity design, server deployment, hardening, monitoring, vulnerability remediation, documentation, and defense exercises.

Plan

Break deliverables into tickets; place upcoming work in Backlog; add a due date, owner, and the appropriate class or team tags.

Execute

Move active work to Doing. Keep the description and comments useful for handoff. Never paste passwords, private keys, tokens, or sensitive personal data.

Verify

Record what was tested and the observed outcome. Link relevant DCWF tasks and add a short first-person reflection describing your contribution.

Close and reflect

Move verified work to Done. Team leads maintain the weekly reflection: what went well, what could improve, and action items.

Visibility is broader than edit rights. Authenticated users can browse boards across teams in a class they can see, and the observer experience is intentionally broad and read-only. Do not put confidential data in tickets, comments, descriptions, team notes, names, or attachments/links.

3. Classes and team views

Select a class

The dashboard separates active and archived class workspaces. A requested class is used only when it is visible to the current user; otherwise the first visible class is selected. Admins can browse every class. Students see enrolled classes. Observers can browse active classes.

Choose the right board view

  • Detailed shows all team boards, with the current user’s teams ordered first.
  • Overview shows the heat-map summary. Select a team to open its focused detail, then use Back to Overview.
  • My Teams shows only teams where you are a recorded member. It is membership-based, not global-role-based, and is not shown to observers.

Each detailed team card has Kanban, Reflection, and Team Notes tabs. The people control expands the roster; the lead is identified.

4. Tickets: preview, edit, filter, move, and reorder

Read a ticket without losing context

  • Hover or keyboard-focus the ticket title for a full title-and-description preview. The preview scrolls when text is long.
  • Click a compact card or its chevron to expand it. Expanded cards show more description, tags, due date, comment count, and assignee.
  • The card background uses the assignee’s color; unassigned work is gray.

Create and edit

Any member of that team can create a ticket. Open the pencil control to edit title, description, status, due date, assignee, and tags. The dialog also contains:

  • DCWF for linking framework Tasks and recording what you did;
  • Comments for team discussion and an audit-friendly handoff.

Admins and team leads can edit applicable tickets. A current team member can edit or move a ticket assigned to them or created by them; losing team membership removes that write permission. Only team members may be selected as an assignee when creating a ticket. The interface uses the shared permission rules to hide write controls when the user lacks permission, and the API remains the enforcement boundary.

Filter

Search matches title or description. Filters support “My Tickets,” a specific assignee or unassigned work, one or more tags (OR matching), and hidden columns. Filters change what is displayed; they do not delete or archive tickets.

Move versus reorder

  • Drag to a different column to change status between Backlog, Doing, and Done.
  • Drag onto another ticket in the same column to change saved order. Reorder rejects cross-team, cross-column, archived, and unauthorized moves.
  • When a filter is active, the server normalizes the complete active column—including hidden tickets—so the saved order remains coherent. Clear the filter and refresh to verify the complete order.
  • If saving fails, the UI restores the prior order and shows an error.
Keyboard note. N, /, M, E, ?, and Esc are registered separately by every visible team board. On multi-board Detailed/My Teams screens, one key can affect multiple boards; use the buttons or focus one team when precision matters. This is a known follow-up.

Archive instead of erase

The ticket’s delete-looking action normally performs a soft archive. A current team lead or current team member who created the ticket can archive it; only an admin can request permanent hard deletion through the API. Archived tickets disappear from ordinary boards and preserve history.

5. Class deliverables and global work tags

Admins open Classes → Deliverables at /admin/classes. Add one or more instructor entries, choose a work type, review the confirmation showing teams and maximum new tickets, then select Distribute to all teams.

  • Each instructor entry becomes an unassigned Backlog ticket on every team in the selected active class.
  • Required work receives the global Required tag.
  • Optional stretch work receives the global Bonus / Extra tag.
  • These global tags are available in every team’s create/edit picker and tag filter.
  • Existing student tickets are not changed or removed.
Idempotence is deliberately narrow. A repeat is skipped only when an active ticket on the same team has the same normalized title and the same global workflow tag. Title comparison trims, collapses whitespace, normalizes Unicode, and ignores case. If someone edits the title, changes/removes the workflow tag, or archives the generated ticket, running distribution again can create a new ticket. Treat those as operational caveats, not duplicate detection bugs.

Distribution is admin-only, blocked for archived classes, uses one serializable database transaction, and appends new items to each Backlog.

Gantt / Timeline

Choose Gantt in the dashboard view selector to see the same tickets grouped by team across a week or month. Filter to one team, expand/collapse team rows, and use Previous, Next, or Today. Bars use assignee colors and display ticket status; overdue markers exclude Done work.

Add an optional Planned start date and Due date through the existing ticket editor. Both are needed for a bar; missing dates leave the ticket in Unscheduled. Creation dates are never used as invented start dates. Tickets outside the current date window are counted separately.

Click a bar or ticket name to open the editor if you have permission; otherwise you get read-only details. Archived classes remain read-only. This first version does not support dragging/resizing bars, dependencies, or automatic scheduling. See the Gantt guide and safe rollout checklist.

6. Student Resources

Admins configure resources under Classes → Student resources at /admin/classes. There are exactly seven optional slots:

  1. Network map
  2. Red Hat
  3. Project tutorial
  4. Visio tutorial
  5. Requirements list
  6. Lab link
  7. Extras

Enter only the class’s actual HTTP or HTTPS destination. Blank slots stay hidden. Do not invent example destinations, and do not include credentials in a URL. Configured links appear in the Student Resources card at the top of that class dashboard and open in a new tab.

Resource-edit conflicts

If another admin saved resources since you loaded them, your save is rejected rather than overwriting their work. Your draft stays visible, but Save is disabled. Copy any draft values you need, then choose Reload latest; this replaces both the displayed values and the comparison baseline. Reapply only the changes you still intend and save again.

Required and Bonus / Extra classifications remain visible on compact ticket cards. A failed drag is rolled back and the board refreshes from the server; wait for the active drag request to finish before starting another.

Finding Team Notes: choose Detailed view or open a team from Overview, then select the Team Notes tab beside Kanban and Reflection. My Tickets appears only on your own teams. To leave a ticket without an owner, select Unassigned.

7. Shared Team Notes and edit conflicts

Each team has one shared note. Team members can edit it; admins can edit; observers and classmates who can view the class may read it. It is explicitly not confidential. Use it for working decisions, handoffs, test windows, and non-sensitive coordination—never secrets or restricted data.

When two people edit

  1. Browser A and Browser B load the same revision.
  2. A saves; the revision increases.
  3. B’s save is rejected with a newer-version warning instead of overwriting A.
  4. Before reloading, B should copy any unsaved text needed for reconciliation to a safe temporary location.
  5. B selects Reload, compares the current note, merges the needed change, and saves again.

There is no live merge, presence indicator, or automatic refresh. A revision conflict is the signal to reconcile manually.

8. DCWF evidence, reports, and weekly reflections

DCWF task evidence

Open a ticket’s DCWF tab. Search or use local-AI suggestions when configured; only framework items of type Task can be linked. Add a concise reflection note describing your own contribution. The link is attributed to the person who created it. If local AI is unavailable, keyword search remains available.

Reports

Reports combine ticket activity, linked DCWF tasks and notes, and work-role alignment. Students may view their own report through the API; team leads can view reports for members of teams they lead; admins can view any report. Observers cannot access individual student reports. Team coverage shows roles touched, contributors, member breakdown, and gaps for authorized team members/admins.

Reflections

The Reflection tab has What Went Well, Could Improve, and Action Items. Only the team lead (or admin) saves the weekly reflection; others read it.

Known follow-up: the dashboard loads only the most recent reflection and initializes the current-week editor from that record. When the latest record is from a previous week, its text is reused in the new week’s editor. Leads must clear or rewrite stale content before saving.

9. Class archive and refresh behavior

Admins archive a completed class from Classes. Archiving preserves its teams, tickets, resources, notes, reflections, and reports while making class-board writes read-only. Admins can open archived boards through the archived-class view and can restore a class.

No real-time updates. The application does not use WebSockets or live subscriptions. After a teammate changes a ticket, resource, reflection, membership, or note, manually reload/refresh the page to see it. A note save can detect a stale revision, but it does not stream the other person’s edits.

10. Recommended student operating routine

  1. Select the correct class and use My Teams or focus the team from Overview.
  2. Refresh before beginning a coordination session.
  3. Review Required and Bonus / Extra filters, due dates, and current Doing work.
  4. Claim or assign work explicitly; keep one observable outcome per ticket where practical.
  5. Update the ticket description/comments with non-sensitive implementation and verification evidence.
  6. Link the DCWF Tasks you actually performed and write a first-person note.
  7. Reorder priorities, then refresh (and clear any filter) to verify saved order.
  8. Update shared Team Notes; reconcile any revision conflict instead of overwriting.
  9. Ask the lead to complete the weekly reflection and check it is for the correct week.
  10. Archive completed work/classes rather than destroying evidence.
