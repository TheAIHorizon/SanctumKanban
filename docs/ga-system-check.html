1. Safety boundary and evidence

Do not run integration checks against a real class database. The guarded script creates users, a class, teams, tickets, resources, notes, tags, and archive state before cleanup. It refuses every database except PostgreSQL at 127.0.0.1:55439/sanctum_ga_check and refuses every app URL except http://127.0.0.1:3459. Still verify both values yourself.

Verification record wording: “See the generated JSON evidence at /tmp/sanctum-kanban-system-check.json (or the explicitly selected output path).” Do not copy a remembered test total into an acceptance statement; totals can change as tests are added.

2. Automated system check (default: no real-database writes)

First stop any npm run dev process for this checkout. The system check runs a production build, and a concurrent development server can collide with the same .next directory.

cd /path/to/SanctumKanban
# Stop the development server for this checkout first.
npm run check:system -- --output /tmp/sanctum-kanban-system-check.json

The default command runs npm test, npm run lint, and npm run build sequentially. It does not run the database-writing GA integration fixture. It performs no HTTP probes unless --url is supplied.

Optional unauthenticated HTTP probes

npm run check:system -- \
  --url http://127.0.0.1:3456 \
  --output /tmp/sanctum-kanban-system-check.json

Use --url only when a compatible app service is actually reachable there; these probes do not log in and do not exercise the integration fixture.

3. Guarded HTTP + database integration fixture

Use a disposable PostgreSQL service mapped to host port 55439, create database sanctum_ga_check, apply the current schema/migrations to that disposable database, then run the application itself on 127.0.0.1:3459 with the same isolated DATABASE_URL. In a second terminal run:

GA_BASE_URL=http://127.0.0.1:3459 \
DATABASE_URL='postgresql://TEST_USER:TEST_PASSWORD@127.0.0.1:55439/sanctum_ga_check?schema=public' \
npm run test:integration

The literal username/password above are placeholders for the disposable database only. The script checks the URL host, port, and database name before any fixture write, uses randomized fixture identities, and attempts cleanup in finally. A guard is risk reduction, not permission to aim it at live data.

8. Troubleshooting

SymptomMeaning / checksSafe response
Connection refused / cannot reach 127.0.0.1:5432The PostgreSQL service/container is stopped, port mapping is absent, or another host/port is configured. This differs from a credential error.Inspect the intended service and its health; for the repository dev database, start the configured db service in docker-compose.dev.yml. Confirm port 5432 before retrying.
Password authentication failedPostgreSQL is reachable, but the database role, password, or authentication rule does not match DATABASE_URL.Verify the intended database role exists and use the correct configured role/password. Do not reset an application user’s password, delete the database, or replace credentials by guesswork.
Missing table/column, Prisma P2021/P2022, or schema mismatchThe service and credentials may be valid, but required migrations/schema have not been applied.Back up the database first, review pending migrations, and apply the approved migration procedure. Never use a reset as troubleshooting.
.next build/dev errorsA dev server and production build may be sharing build output.Stop the dev server, remove only disposable build output if appropriate, then rerun the system check. Do not touch database state.
HTTP probe failsThe URL is wrong, service is down, redirect/status differs, or request timed out.Verify the exact service and URL. The optional probe expects login 200, providers 200, and unauthenticated tickets 401.
Migration rule: make and verify a backup before schema migration. Do not run prisma migrate reset, drop the database, remove the PostgreSQL volume, or reseed a real class database to “fix” a missing schema.

Database check and recorded execution

To catch a stopped database, invalid connection configuration, or missing schema without changing data, run the following with the same DATABASE_URL as the intended app:

node scripts/database-check.mjs
# Or include it with test/lint/build (stop this checkout's app first):
npm run check:system -- --database --output /tmp/sanctum-kanban-system-check.json

This checks connectivity and required table/column metadata; it does not seed, migrate, or read user records. A passed database check does not prove that a user's password is correct.
