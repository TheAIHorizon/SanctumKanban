Automatic completion tracking

Compare the planned end of a ticket with when it was marked Done—without entering an actual finish date manually.

How it works

ActionResult
Doing → Done, or Backlog → DoneThe server records the actual completion timestamp automatically.
Create a ticket directly as Done through the APICompletion is recorded when created.
Edit or reorder a ticket already DoneThe existing completion timestamp stays unchanged.
Done → Doing or BacklogThe current completion timestamp is cleared; history retains the previous completion.
Complete the reopened ticket againA new completion timestamp is recorded, with transition history preserved.
Older Done ticket with no recorded completionShows “Completion date not recorded.” The app does not guess from creation or update dates.

Actual completion is a read-only, server-managed field. Direct attempts to submit completedAt are rejected. This timestamp records when the app received the completion transition, not independent proof of when the work physically finished.

Reading the Gantt chart

  • Assignee-colored bar: the planned start and expected end.
  • Diamond: actual completion date.
  • Finished late: solid red extension from expected end to actual completion, with a label such as “3 days late.”
  • Finished early: completion diamond before expected end, a faded remainder of the planned bar, and an early label.
  • Finished on time: completion marker at the expected end with “Completed on time.”
  • Not finished but overdue: dashed red extension to today, labeled “Overdue—not completed.” This is not treated as an actual finish.
  • Planned dates outside the displayed window: the row still appears when its actual completion marker or overrun intersects the current window.
  • Missing planned dates: the ticket remains Unscheduled; recorded completion can still be shown in its details.

Click a row, bar, or completion diamond to inspect the ticket. Authorized users see the editor with the automatic timestamp displayed read-only. Observer, peer-team, and archived views remain read-only. Opening Gantt refreshes server data so recent Kanban transitions appear without a full page reload.

Date convention: early/late differences compare UTC calendar dates, not fractional elapsed days. Actual timestamps are stored as instants and displayed with UTC identified. Near midnight, the UTC calendar day can differ from your local day. Planned start and due dates are not automatically overwritten on completion.

This is not an immutable grading baseline: authorized users can still edit planned dates under existing permissions. The comparison uses the ticket's current expected end date. Locking an original commitment or maintaining approved schedule revisions would be a separate feature.

GA checks

  1. Move an owned Doing ticket to Done. Verify the timestamp appears automatically and the planned dates stay unchanged.
  2. Reload and confirm the timestamp persists. Edit only the description, then submit Done again; confirm the timestamp is identical.
  3. Reopen it, confirm current completion clears, then finish again. Verify the earlier finish remains in history.
  4. Check early, on-time, late, and still-overdue cases. Distinguish solid from dashed red tails.
  5. Check a legacy Done ticket: no date should be invented.
  6. Check an actual completion in the current month whose planned bar was in an earlier month.
  7. Verify observers and non-authorized teammates cannot change ticket status; archived classes stay read-only.
  8. Run the guarded local integration check for concurrent initial Done requests; one transition should produce one stable timestamp and one moved-history entry.

Verified local results

120 automated tests, 23 real HTTP/database scenarios, and 10 browser scenarios passed. Lint, production build, TypeScript, and database/schema checks passed. The final targeted independent review passed after making ticket creation and its history atomic. Tests include concurrent initial Done transitions, duplicate Done requests, reopening, direct Done creation, denied manual timestamps, preserved plans, actual-only timeline windows, and browser switching from Kanban to Gantt. Existing warnings and the separately documented authorization backlog remain.

Original local Alpha–Echo demo counts remain 10, 20, 30, 40, and 50. Screenshots use synthetic QA cases; historical completion dates were not invented for the original demo. The local preview was restarted with the update. The live NAS was not changed.

Deployment boundary

This update is built and verified locally. Publishing source on GitHub does not deploy it to the live student NAS.

The additive migration prisma/migrations/20260916_add_ticket_completed_at/migration.sql adds a nullable completion timestamp with no historical backfill. For a later approved NAS rollout: preserve a consistent database backup and the previous image; rehearse on a restored copy; verify counts and the existing start-date migration; apply the reviewed schema update and new image during a maintenance window. Do not reset or seed the live database. If rolling back the image, retain the nullable column so newly captured completion evidence is not discarded.

Pre-existing authorization findings remain documented in the code review; completion tracking does not constitute a comprehensive security audit.
